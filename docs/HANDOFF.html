Moving this to your PC

This session runs in a disposable cloud container — its disk vanishes when the session ends. Nothing here depends on that container surviving. Everything durable is on the branch:

# everything lives here
git clone -b claude/clover-studio-scene \
  https://github.com/cmathew654-dot/money-map-generator.git clover-studio
cd clover-studio

# Blender 5.x as a pip module — no Blender install needed. Python 3.13 exactly.
py -3.13 -m venv .venv
.venv\Scripts\pip install -r requirements.txt

# render the still (~9 min on 4 cores)
.venv\Scripts\python -m scene.build --samples 96 --width 1600 --height 900

# rebuild the browser page (4s — resumes from export\work.blend)
cd web && npm install && ..\.venv\Scripts\python build.py
python -m http.server 8777 --directory dist

# or open it in Blender 5.2+ (the .blend will not open in 4.x)
blender renders\clover-studio.blend

Fonts. Text uses Liberation Sans on Linux and falls back to Arial on Windows/mac — the two are metric-compatible, so layout holds. A warning prints if neither is found. Set CLOVER_FONT_DIR to a folder of Liberation TTFs to pin exact faces.

You started this from the Claude app, so it's a Claude Code session in a remote container — not Remote Control. On your PC, open claude.ai/code, find this session and resume it in the browser; same conversation, same container while it lives.

How the scene is built

Nothing is downloaded. Every mesh is generated from code and every material is a shader network, so the image is reproducible from source alone.

Two things worth knowing

The monitor is lofted from superellipse cross-sections rather than modelled as a rounded box. That is what produces a CRT's boxy bezel, straight sides and hard taper to the neck.

The screen is not a texture. The Win95 chrome, the browser and the page are real emissive geometry on a virtual 640×480 raster, so the interface genuinely lights the desk in front of it in the Cycles render.

The live page in the CRT

CSS3DRenderer transforms a real <iframe> into the same 3D space as the WebGL scene. The two layers share no depth buffer, so the DOM would float over the monitor's own bezel. The fix: the DOM layer sits behind a transparent WebGL canvas, and a depth-only plane on the screen's exact transform punches a hole for it to show through. Anything genuinely in front still writes depth and still occludes.

To point it at your real site, set SITE_URL at the top of web/src/app.js and rebuild; left empty, the bundled stub loads via srcdoc. Two constraints:

  • Cross-origin. A site sending X-Frame-Options: DENY or a tight frame-ancestors CSP will not load. Check with curl -sI <site> | grep -iE 'x-frame|frame-ancestors'. A real URL also only works when the page is self-hosted — the Claude artifact sandbox blocks it.
  • No post-processing reaches the DOM layer. Bloom, grading and the CRT glass never touch those pixels. A translucent WebGL overlay in front works; the content itself stays ungraded.

What a second model found

Before finalising, a separate reviewer tried to reproduce the three outputs from the repo alone and read the code adversarially. Its verdict on direction: three.js + CSS3D is right; nothing in the end goal needs another engine. Its verdict on rebuildability was that the web page could not be rebuilt from a clone — every build step lived in a session scratchpad. That is fixed: web/build.py reproduces the page in 4 seconds, verified. The full list, each item marked fixed or open, is in docs/REVIEW-2026-09-06.md. Two of its refinements are now on the roadmap.

One correction to earlier claims: the iOS screenshots in this session came from Chromium with an iPhone user agent, not WebKit. They validated layout and touch wiring, not Safari.

Constraints found the hard way

Background processes do not survive session idle

Two lighting bakes died within minutes of the conversation going quiet — not OOM, not segfault. This container suspends background work. Long jobs must be resumable: bake_lightmaps and bake_vertex_lighting now write progress as it lands, skip finished work and stop on a time budget. Both then completed in foreground chunks with zero failures.

Never export Blender's lights to glTF

They convert to physical units: the sun arrived at 5,327 lux and the desk lamp at 6,413 candela, against runtime lights tuned between 0.5 and 5.5. The entire room rendered pure white. export_glb now defaults lights off and the runtime strips any that arrive.

glTF cannot carry a node graph

Seven materials drive Base Color procedurally — the desk, floor, brick and every plant. They exported as flat white. flatten_procedural_colors assigns each a representative value before export; the proper fix is the albedo bake, already produced.

Shipping COLOR_0 forces vertex colours on

GLTFLoader sets material.vertexColors = true whenever the attribute is present, so merely including it multiplies the bake into every albedo whether the runtime asks or not. export_glb defaults vertex_colors=False.

Why the vertex bake is off

All 954 props baked successfully and the data is in export/work.blend. The web build does not use it, because it is a visible regression: a COMBINED bake at 20 samples across a prop with a handful of vertices carries almost no signal, and gltfpack's simplification plus 8-bit colour quantisation finish it off. The wall wedge is a single triangle and came back black; the monitor came back dark green.

To make it work, a future pass needs to subdivide props before baking, raise samples, and skip decimation on anything vertex-lit. Until then, lightmapped statics with runtime-lit props looks considerably better. Flip USE_VERTEX_COLORS in the app to compare.

What I would do next

  1. Build the exterior. Street, storefront, door. The walk-in is the framing device for the whole demo and none of it exists yet — this is real modelling, not export work.
  2. Point the CRT at the real site and confirm it renders inside the monitor. One line, but it needs the header check above.
  3. Remove the iOS risk rather than test for it. When seated the camera is locked, so a plain 2D iframe positioned over the screen rect behaves identically and drops the 3D-transformed iframe — the one historically fragile piece on mobile Safari. Screenshot texture at distance, flat iframe when close. Then confirm on a physical iPhone; everything mobile so far ran in Chromium with an iPhone user agent.
  4. Fix the lightmap grade, then compress. Bakes are 8-bit PNG with no view transform, so highlights clip and the room drifts from the still — the back room blows out. Bake to float or apply exposure before saving. Then KTX2/Basis; iOS Safari kills tabs around 1–1.5 GB.
  5. Redo the vertex bake properly, or drop it and lightmap the largest props individually instead.

If it goes to an Unreal artist instead

For a browser demo, don't — Unreal has no HTML5 target, so it means Pixel Streaming: a GPU per concurrent visitor. And the live-web-page trick inverts, being trivial in three.js and awkward in Unreal. Unreal earns its place only if this becomes a VR or installation piece.

If it does go: geometry imports at 1:1 (authored in real metres, uniform scale 100), Nanite handles the triangle count trivially, and the Python is the real asset because it is parametric. Rebuild the materials natively or use the baked albedo set; relight from scratch, since Cycles values are not Lumen values.
